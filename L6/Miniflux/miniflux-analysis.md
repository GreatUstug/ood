# Анализ архитектуры Miniflux (версия 2.3.5)

## 1. Введение

В данной работе исследуется архитектура **Miniflux** — приложения с открытым исходным кодом для чтения RSS/Atom/JSON Feed. Рассматривается **базовая конфигурация** из файла `contrib/docker-compose/basic.yml`.

## 2. C1 — System Context

Диаграмма C1 показывает, кто использует систему и с какими внешними системами она взаимодействует.

**Элементы:**
- **Reader (Пользователь)** — читает статьи и управляет фидами через веб-интерфейс.
- **Admin (Администратор)** — настраивает систему, управляет пользователями и глобальными параметрами (в базовой конфигурации может совпадать с Reader).
- **Miniflux** — центральная система, агрегирующая и отображающая контент.
- **Feed Sources (Внешние системы)** — веб-сайты, отдающие RSS/Atom/JSON.
- **PostgreSQL (Внешняя система)** — база данных, где хранится всё состояние.

**Основные связи:**
- `Reader/Admin` → `Miniflux`: HTTPS (веб-интерфейс / API).
- `Miniflux` → `Feed Sources`: HTTP GET (забор фидов).
- `Miniflux` → `PostgreSQL`: SQL (чтение/запись данных).

## 3. C2 — Container

Диаграмма C2 раскрывает внутреннее устройство Miniflux.

**Элементы:**
- **Miniflux Application (Go)** — единый статически скомпилированный бинарник. Включает в себя:
    - **HTTP Server / Web UI** (Vanilla JS, HTML/CSS).
    - **REST API / Google Reader API / Fever API** (для клиентов).
    - **Feed Processing Pipeline** (fetcher, parser, sanitizer).
    - **Storage Layer** (direct SQL, без ORM).
- **PostgreSQL** — реляционная база данных (хранение фидов, статей, пользователей).
- **Feed Sources** — внешние источники контента.

**Основные связи:**
- `Miniflux Application` → `PostgreSQL`: SQL-запросы (direct SQL).
- `Miniflux Application` → `Feed Sources`: HTTP GET.

*Схема C2 представлена в файле `miniflux-c2.mmd` (и экспортирована в PNG).*
